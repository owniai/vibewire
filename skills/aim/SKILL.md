# Aim: From Task to Plan

## Overview

读取项目上下文，澄清需求，评估任务规模并路由到对应流程。

<HARD-GATE>
aim 只做三件事：探索项目上下文、澄清需求、路由。禁止编写任何代码（测试、实现、配置），禁止深入研究技术方案、探索解决方案或设计架构——这些是路由后流程的职责。
</HARD-GATE>


## Process

### 1. Explore Project Context

读取项目文档与历史经验：
- `.vibewire/project.md` 和 `.vibewire/CHANGELOG.md` — 项目全貌。若不存在，提示用户先运行 `/vibewire:intro`
- `.vibewire/tech-research/knowledge.md`（若存在）— 全局技术调研知识库（简要结论、途径、经验）
- `.vibewire/evolve.md`（若存在）— 历史执行经验，用于规避已知的陷阱和偏差模式

聚焦探索与本次任务相关的模块：先通过 Skill 工具加载 `peek-code:peek-code` skill，再用 `peek` 基于签名快速定位相关定义，最后仅深入阅读评估本次变更所必需的文件，不发散探索无关模块

### 2. Clarify Requirements

使用 AskUserQuestion 工具逐一提问以澄清需求：
- 每条消息只问一个问题 — 如果某个主题需要更多探索，将其拆分为多个按顺序逐个问题
- 重点关注：目的、约束、成功标准
- 宁可多问一句，也不要带着模糊理解前进
- 充分理解后，呈现目标摘要供用户确认
- 用户确认后方可继续，如需修改则重新讨论

**澄清边界：** aim 只澄清 what 和 why——用户要什么、为什么、有什么限制。不探索 how（方案选择、技术调研、架构设计），这些由路由后的流程负责。

### 3. Assess Task Scope & Route

基于项目上下文和澄清结果判断任务应走哪个流程。

**走 vibe — 非实现任务：**
- 用户的意图不是变更代码，而是理解、分析、调研、讨论或执行操作
- 产出物是认知（分析报告、调研结论、方案建议）或操作结果，不是可部署的代码变更
- 典型场景：架构分析、技术选型、性能瓶颈分析、可行性评估、方案对比、git 操作、部署检查、纯讨论

**走 snap — 小型任务：**
- 变更不引入需要审查的复杂新职责，代码逻辑直截了当
- 即使新增简单文件（工具函数、类型定义、配置），只要不涉及复杂逻辑即可
- 典型场景：bug 修复、新增/重写函数、配置调整、简单性能优化、补充测试、安全修复、机械性重构、简单接口扩展、引入新依赖但用法明确

**走 build — 常规任务：**
- 引入了需要审查的新职责或结构性变更（新增模块/子系统、跨模块协调、第三方集成等）
- **可以在单次执行中连贯完成**——这是 build 的核心约束：任务复杂度在单次执行的承载范围内
- 即使涉及多模块、多层、多步骤，只要整体可一次完成且不导致认知超载，仍走 build
- 判定关键：任务是否可在一次完整流程中从设计探索到提交全部完成

**走 plan — 复杂任务：**
- **无法单次连贯完成**——关注点过多 + 任务量大，单次执行会导致认知超载
- 存在可独立交付的阶段，阶段产出可被下游消费（如前置重构有独立价值、数据流分层中每层可独立验证）
- 复杂任务倾向于 plan——宁可多规划，避免在中途发现承载不了
- 判定关键：是否需要拆分为多个 stage，每个 stage 可独立执行

**路由：** 读取对应的流程文件（与本文件同目录）并按其指引执行。路由后，aim 职责结束。
- vibe → `vibe.md`
- snap → `snap.md`
- build → `build.md`
- plan → `plan.md`

使用 AskUserQuestion 始终展示全部四个路由选项，附简短说明，并给出推荐及推荐理由，由用户确认：
- **vibe** — 非代码实现任务（分析、调研、讨论、操作）
- **snap** — 小型代码变更（逻辑直截，无需审查）
- **build** — 常规代码变更（单次可连贯完成）
- **plan** — 复杂代码变更（需拆分阶段）

## Key Principles

- **聚焦探索上下文** — 仅读取与本次任务相关的文件，充分但不发散
- **一次一个问题** — 不用多个问题淹没用户
- **禁止深入设计方案** - how 由路由后的流程负责，三个流程均支持按需调用技术调研和实验，技术不确定性不影响路由
- **充分识别任务特征** - 设计探索阶段必须充分识别任务特征，确保路由准确——不应在执行过程中升级流程
- **善用 subagent** — 只需要结果、不需要自己深入细节的探索任务，委托 subagent 执行。代码实现阶段同样适用：机械性任务（批量重命名、模板化修改、重复性重构）推荐委托 subagent；重复性任务先完成一个样板确认模式，再交由 subagent 批量执行
- **忽略格式检查** — markdown lint 等文档格式告警一律忽略，内部规划文档不适用项目文档格式规范

## Anti-Pattern

- **"不读代码直接规划"** — 跳过上下文探索就评估任务，导致规划与现有实现脱节
- **"顺手写点代码"** — aim 阶段严禁编写任何代码，即使看起来很简单的修复也必须路由后再执行
- **"路由后直接实现"** — 路由后必须先读取流程文件，按流程文件的步骤和约束执行，不得跳过流程直接动手
- **"边澄清边设计方案"** — 澄清需求时同步探索解决方案或研究技术选型，模糊了 aim 和路由后流程的职责边界。澄清只关注 what 和 why，how 留给路由后的流程
- **"需求很明确，跳过澄清"** — 即使用户表述清晰，仍需确认目的、约束和成功标准。跳过澄清直接路由，常导致选错流程
