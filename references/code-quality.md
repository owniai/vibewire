# 代码质量审查参考

检查反模式、坏味道和设计缺陷。关注影响可维护性和正确性的实质问题。

## 检查清单

### 冗余状态

- 状态是否重复了已有的状态（可以从中派生）
- 缓存值是否可以直接计算得出
- 是否有不必要的 observer/effect，可以直接调用

### 参数蔓延

- 函数参数是否越来越多，应该重构为接收配置对象
- 是否通过添加参数来处理变体，而非抽象统一逻辑
- 回调函数的参数列表是否过于复杂

### 复制粘贴变体

- 是否有几乎相同的代码块，仅有一两处差异
- 差异部分是否可以通过参数或策略模式统一
- 复制粘贴的代码是否同步更新了修复

### 泄漏抽象

- 是否暴露了内部实现细节（私有属性被外部直接访问）
- 是否跨越了抽象层级（高层直接操作底层数据结构）
- 返回值是否泄漏了内部表示（应返回副本或不可变视图）

### 字符串类型化

- 是否使用原始字符串表示本应是常量、枚举或 branded type 的值
- 魔术字符串是否应提取为命名常量
- 类型区分是否依赖字符串比较而非类型系统

### 不必要的复杂性

- 是否引入了不需要的抽象层
- 简单问题是否有过度设计
- 是否有可以删除的死代码

### 不必要的注释

- 注释是否在解释代码做了什么（函数名已足够清晰时应删除）
- 注释是否在叙述变更历史（应由 git 记录）
- 只保留解释"为什么"的注释（隐藏约束、微妙的不变量、变通方案）

### 错误处理

- 是否吞掉了异常而未处理
- 错误信息是否足够明确，便于定位问题
- 是否有未处理的边界情况

## 严重级别判定

| 级别 | 典型场景 |
|------|---------|
| **blocking** | 泄漏抽象导致数据不一致；未处理的错误导致潜在崩溃；关键逻辑存在 bug |
| **major** | 复制粘贴变体导致维护风险；参数蔓延影响可读性；魔术字符串导致运行时错误风险 |
| **minor** | 不必要的注释；命名可以更好但不影响理解；轻微的代码风格问题 |

## 审查方法

1. 读取变更的代码文件
2. 逐文件检查上述清单中的各项
3. 重点检查 implementer-log.md 中标记的关键实现
4. 对可疑模式进行交叉验证（搜索是否为孤立问题还是系统性问题）
5. 记录发现，附上具体行号和代码片段
